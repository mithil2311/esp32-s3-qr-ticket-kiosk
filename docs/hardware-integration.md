# Hardware integration checklist

This checklist identifies pending real hardware verification, not tested hardware results. Both firmware configurations compile; no physical board, scanner, printer or GPIO was attached for this work.

- Confirm the exact GM75 module/connector revision, pin labels, supply requirements, current demand, UART voltage levels and output terminator from the actual unit documentation. Verify 115200 8N1 and decoded-string output. The software's CR/LF text framing is configurable by modifying/configuring the scanner to match; it is not a verified factory default.
- The supplied labels read scanner RX→GPIO17, scanner TX→GPIO18, so defaults are ESP TX17/RX18. Verify the perspective before wiring. GPIO4/5/6 are configurable indicator defaults. Check the chosen module's strapping, flash/PSRAM, USB and unavailable GPIO restrictions and reject overlapping pin assignments.
- Verify supply rails, common ground, protection and signal compatibility. Use a suitable buzzer driver; do not drive an unspecified buzzer load directly from an ESP GPIO. A circuit/PCB design must separately apply Mithil's standing PCB rules; no circuit design is delivered here.
- Identify the exact SHREYANS KP307-UB interface and firmware from its nameplate, manual and enumeration. Do **not** infer TTL UART from the model name. Record USB VID/PID/descriptors and endpoints, USB class/protocol, or verified Bluetooth profile and pairing behavior. Confirm ESC/POS command compatibility, code pages, cut behavior, power/current needs and status semantics on this actual unit.
- Implement USB Host or Bluetooth transport as a separate `Printer` implementation. Allocate VBUS/power and host wiring only after confirming the transport. Neither USB printer class, CDC-ACM, vendor protocol, SPP, BLE nor status command set is assumed by the current code.
- Map printer acceptance, definite no-start and uncertainty carefully. A write/USB transfer ACK confirms bytes only. A status reply must be correlated to the specific job and its physical completion before returning `Confirmed`. If the device cannot prove that, return `Uncertain` and require operator inspection. Cutter failure is uncertain even if some paper emerged.
- Preserve the durable PRINTING barrier before any transport side effect. Never automatically reprint an uncertain job. Test disconnects at every transfer boundary, paper-out after partial output, cutter jams and ambiguous status responses with the real printer.
- Provision a unique persistent device ID, actual backend endpoint and Wi-Fi credentials in the hardware config. Verify reconnects and bounded timeouts. Production TLS, certificate trust, authenticated kiosk/operator access and protected credentials need deployment integration; the local FastAPI test server is not a production service.
- Provide an authenticated operator interface invoking `Controller::retry()` or `resolve_printed()`. Hardware builds intentionally disable simulation UART operator commands. Record operator identity/evidence externally. An unverified outcome remains quarantined; releasing or replacing it requires a separately specified admission policy.
- Qualify NVS wear and power-loss integrity at deployment transaction volumes. The sample uses the default NVS partition and writes at every safety boundary. Never erase NVS automatically on initialization errors or as a recovery shortcut. Retain reservations and backup backend records during upgrades.
- Test physical power loss after CREATED, RESERVED, PRINTING, CONFIRMED and server commit; test real flash brownout and watchdog behavior. The QEMU test terminates the process and restarts persistent emulated flash; it does not model analog brownout/torn writes.
- Measure actual scanner-to-app latency, printer completion behavior, GPIO pulses, heap, stack margins, UART framing/parity/overflow errors, queue pressure, Wi-Fi outages and long-run thermal/power behavior on hardware. QEMU and native benchmark numbers cannot substitute for these results.
